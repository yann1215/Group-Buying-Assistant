# 无盈利拼团小助手 Group-Buying-Assistant

## 会话类型

侧栏保留一个「＋ 新对话」按钮，对话列表仅显示名称。新对话初始为未分类，只保存公共会话信息。
输入有效群聊名称或订单后归为单车；输入“合发”后归为合发，也支持校验通过后用“合发：车1，车2”归类。
合发查询或输出指令可以确定类型，尚未设置车序时会提示录入。普通聊天和改名不会确定类型，
归类前直接查看订单、算均摊、算大货等会提示先录入群名或订单，无效录入也不会锁定类型。
一条消息混合两类业务操作时请分开输入。类型一旦确定，后续指令不会自动转换类型。

- 单车会话：登记群名、订单版本，查看或比较订单，核对成员，设置特殊成员与参摊配置，计算均摊和大货。
- 合发会话：逐个登记车群及订单，设置或查看合发车序，生成合发清单，刷新合发身份映射；不录入均摊、大货配置。
- 两类都支持普通聊天和修改会话名称。输入另一类的业务指令会提示进入对应会话，不修改业务数据。

旧数据库在启动时自动迁移：已有单车、合发会话保留类型；确认没有聊天记录、群名和业务数据的默认空白会话恢复为未分类。
旧合发会话如同时含单车数据，会显示核对提示；原始配置及订单路径保存在上下文 `legacy_context`，
不作为合发的活动业务数据。删除该会话时备份随文件归档。

## 软件帮助

在任意会话中输入 `帮助`、`软件有哪些功能`、`均摊怎么操作`、`合发表的指令是什么` 或
`如何分析转单记录`，LLM 会根据内置的软件使用说明，解释功能、适用会话和指令示例。
示例中的群名、文件名、昵称和金额需要换成实际参数，再单独发送操作指令。
帮助咨询只回答问题，不修改配置、不读取微信、不执行计算，也不消费当前等待确认。
帮助资料保存在 `app/llm/prompts/software_help.md`，与转单判定知识库 `knowledge/knowledge.md` 分开维护。

## 转单分析

单车会话输入 `比对转单记录`、`分析转单记录` 或 `查找转单异常`，先展示当前旧订单、新订单（旧 → 新）、
聊天记录的时间范围与复用/提取方式、特别关注商品。确认信息与执行提示之间空一行。
回复 `确认分析`、`确认`、`是`、`yes`、`y`、`1`、`对`、`无误`、`没问题` 执行；英文忽略大小写，
去除首尾空格后按完整回复匹配，仅在等待转单分析确认时有效。`取消分析` 取消；开始其他业务操作会结束此确认状态。

可随指令录入或单独修改关注信息，例如 `分析转单记录，特别关注：商品A缺少3件；商品B数量异常`、
`特别关注：商品A：缺少5件`，多项用逗号、分号或换行分隔；未提供缺少数量时标记为未知。
`特别关注：无` 清空。关注信息保存到当前会话并提交模型，作为待核查线索。
修改后需确认最新信息；确认时订单内容、聊天来源或复用状态变化，也需重新确认。

确认后，复用当前两份订单路径、内容哈希及群聊均匹配且未损坏的报告，否则自动比对，不再单独确认。
手动 `比较订单` 生成的报告也可复用；缺少来源内容元数据的历史报告重新生成。
聊天记录按成功获取时间判断：不足十分钟且当前群聊的筛选文件有效则复用，包含手动获取的其他时长。
已满十分钟、文件缺失或无法验证来源/获取时间时，自动提取确认执行时刻往前一周的记录并筛选。
确认页自动提取的具体时间为预计范围，最终截至确认执行时刻。不覆盖用户保存的手动时间偏好。
自动提取不再另行确认；`获取聊天记录` 始终主动提取，可通过 `获取近1个月的聊天记录` 等指定其他时长。
提取失败保留旧文件并停止分析。

分析输入保存到 `workspace/<会话ID>/transfer_analysis_input.json`，包含订单比对 CSV 内容、筛选聊天 CSV 内容、
时间范围、来源和特别关注商品。默认通过 `llama-cpp-python` 直接运行 Qwen3 1.7B GGUF 专用模块分析，不生成模拟分析结论。
工具调度器的 `transfer_analysis_client` 注入实现 `analyze(payload) -> str` 的客户端；
返回实际结果文本，接口失败时保留已准备的输入。聊天记录元数据、报告索引、关注信息及待确认信息随会话保存。

### 本地 Qwen3 模型与知识库

默认模型为官方 `Qwen3-1.7B-Q8_0.gguf`，通过 `llama-cpp-python` 直接加载，无需 Ollama 或后台服务。
源码环境在项目根目录执行 `powershell -ExecutionPolicy Bypass -File scripts/setup_llama.ps1`：
安装固定版本 Windows CPU 推理库、下载固定版本模型并验证 SHA256，成功后移除项目虚拟环境的旧 Ollama Python 客户端。
已有模型将校验后复用，网络中断保留 `.part` 文件供续传。
模型默认存放 `models/Qwen3-1.7B-Q8_0.gguf`，可通过环境变量 `GROUP_BUYING_MODEL_PATH` 指定其他位置。
CPU 线程数、GPU 层数、上下文大小及两个模块的输出长度在 `app/config.py` 配置。
默认 CPU 版本，启用 GPU 需安装对应构建并调整 GPU 层数；不需要安装 PyTorch 或 Transformers。
两个模块共用一个惰性加载的模型实例，串行推理，采用 Qwen3 非思考模板和 JSON Schema grammar 约束。
输入按实际 token 数检查预算，不静默截断；输出达到长度上限时报告不完整。
模型共用一个底座，指令规范化和转单分析分别使用独立 prompt 与 Pydantic schema，不共享对话上下文。
明确指令沿用规则流程；模糊指令通过模型规范化后交回 `intent_parser`，咨询、否定或歧义不能直接升级为操作。
模型不可用或返回无效数据时提示错误，不执行推测的业务操作。

PyInstaller 的 onedir 包包含推理 DLL、模型和模型许可证；可在 exe 同目录 `models/` 放置默认文件名的模型覆盖内置文件。
首次调用模型会加载权重，可能比后续调用慢；无需联网即可推理。
可执行 `.venv/Scripts/python.exe scripts/verify_llama.py`，使用固定样例验证指令规范化和转单分析的真实推理，不读取实际订单或微信。

知识库读取 `knowledge/knowledge.md`（UTF-8 Markdown），相关章节作为解释依据，用户特别关注仍是待核实线索。
每次分析记录知识库内容哈希，无需重新训练模型；打包内置默认知识库，exe 同目录的同路径文件可覆盖默认版本。
分析输入增加新旧订单快照、编号后的聊天消息、订单差异和知识章节。
完整聊天文件内容签名有效时使用同次导出的文本/引用消息，包含纯确认上下文；旧元数据缺少签名时使用筛选记录并说明限制。
消息、差异、知识章节分别使用 `M`、`D`、`K` 编号，引用可在 `transfer_analysis_input.json` 查阅。
长聊天按字符预算分段并重叠三条消息。超出关联上下文预算会明确提示缩小范围，不静默截断资料。
模型提取转单事件，程序核对净数量，再由模型解释订单差异；不存在的证据引用会拒绝。
已确认事件须引用转出与接收的不同消息；生成阶段限制可用引用编号和字段状态组合。
无证据引用的模型自由备注仅保存在结构化结果的 `unverified_model_notes`，不作为已核查事实显示。
分析结果保存为 `workspace/<会话ID>/transfer_analysis_result.json`，回复提供文件入口。
缺少聊天证据、取消/改口、身份或商品不能唯一确定时保留待核实；远距离跨段关联与整单转让仍需人工核查。

## 转单期聊天记录

仅在单车会话使用，前置条件只需设置车名（现有的群聊名称），无需订单、成员核对或均摊配置。
输入 `提取转单期聊天记录`、`获取聊天记录`、`提取近1周的聊天记录` 或
`提取转单期聊天记录，时间1个月`。`转单记录` 为保留词，不触发本功能。
时间初始默认最近1周；指定后保存到当前车，后续请求和重启后沿用，直到再次修改。
支持正整数小时、天、周（星期/礼拜）、月、年，中文数字支持一至九十九（含“两”）。
每次以执行时刻重新计算北京时间范围，月/年按日历回溯，月末取目标月份的最后一个有效日期。
也支持 `提取聊天记录，从9.1开始`、`提取聊天记录，从9月10日开始`、
`提取聊天记录，从10月3开始`，默认从指定日期北京时间 00:00 提取至执行时刻。
未写年份时按设置当年解析，支持明确年份（例如 `从2026年9月1日开始` 或 `从2026-09-01开始`）。
开始日期保存为具体年月日，重启或跨年仍沿用；再次输入相对范围可切回最近几天/几周模式。
无效日期、未来日期或同时指定开始日期和相对范围时提示修正，不修改原设置。

筛选文件仅保留“类型”为 `文本` 或 `引用消息` 的记录，且“内容”列包含
`转单`、`转`、`接`、`合单`、`合`、`核弹`、`给`、`掰`、`吐` 中任意一项，或包含 `@`。
仅包含数字不作为保留条件。
内容按字面包含匹配；消息 ID、时间、wxid、昵称等其他列不参与内容匹配。
筛选文件删除“消息ID”和“备注”列，其余字段、消息内容与顺序不变；未筛选文件仍保留所有类型的全部记录及原始全部列。
同时保存未筛选的完整记录和筛选后的记录，两份均使用获取函数默认的 CSV 格式及 UTF-8 BOM 编码。
筛选文件：`workspace/<会话ID>/<群聊wxid>.csv`，例如 `workspace/12/123456789@chatroom.csv`。
未筛选文件：`workspace/<会话ID>/<群聊wxid>_unfiltered.csv`。
文件名使用实际微信群 ID，不使用车名或群聊显示名称。
再次导出成功时更新两份同名文件；失败时保留已有文件。没有匹配消息时筛选文件只有表头，未筛选文件仍保留全部记录。

## 跨车合发与补邮清单

新对话输入 `合发` 即可设置为合发对话，随后逐个录入 `车名 aaa，订单 order1`、
`车群 bbb，文件 order2`（也支持 `车1 aaa，订单 order1`）。车群按录入顺序编号，
每次录入显示已保存信息和当前数量；至少两个车群后，输入 `输出合发表` 计算合发补邮清单。
无需预先建立单车会话。订单文件名未带后缀时自动补 `.xlsx`，从 `orders/input/` 查找；
也支持完整路径。订单文件无效或车群重复时不增加数量。再次输入 `合发` 保留已录入信息。

先在各单车会话中登记群聊名称及原始 `.xlsx` 订单，再点击「＋ 新对话」并输入
`合发：车1，车2，车3` 保存车序（支持中文、英文逗号）。冒号后的所有内容均作为车名，
须与已登记群聊名称精确对应。关联成功后以单车会话 ID 保存，单车群名修改后仍保持关联；
来源会话删除后不会自动关联到同名新会话，需要重新录入车序。随后输入 `输出合发表` 生成 Excel；也支持
`查询合发表`、`输出合发补邮`、`给我合发清单`、`合发补邮表格`、`订单合并`。
输入 `查看合发车名` 或 `查看合发订单`，按车序逐行列出 `1. 车1：order1.xlsx` 等当前最新订单信息。
这两个指令仅用于合发会话，与单车会话的 `查看订单` 指令不同。
录入合发配置后，对话名称默认使用对话创建日期（北京时间）的 `YYMMDD合发`（例如 `261005合发`），
文件名为 `261005合发_补邮清单_车1_车2_车3.xlsx`，车名按录入顺序排列。
跨天输出、重新录入车序均沿用创建日期，同名文件重新生成时覆盖更新。
输入 `修改会话名称为合发5.0` 可自定义会话名称，后续录入、保存和输出沿用该名称，
也支持 `修改对话 合发测试`、`对话改为 合发测试` 等表达，改名直接执行，不调用模型。
文件名相应变为 `合发5.0_补邮清单_车1_车2_车3.xlsx`（文件名非法字符替换为下划线）。

每次生成均读取各车最新原始订单，身份映射优先复用本合发对话的
`workspace/<会话ID>/order_identity_mapping.json`。所需身份完整且 wxid、微信昵称、订单昵称无冲突时，
不读取微信成员，不重新解析身份；仅缺失或有歧义的订单补查对应车群。
缓存包括身份三项、来源车会话 ID、单号、匹配依据和验证时间，会话改名后仍可复用。
商品和地址始终使用最新订单。身份补查与既有映射冲突时中止，保留旧缓存；
输入 `刷新合发映射` 可重新读取全部选中车群，校验通过后重建缓存并输出表格。
损坏或无法识别的缓存会重新解析，成功导出后才原子更新缓存。
不执行完整成员检查，也不修改特殊成员或商品配置。
wxid 和订单昵称为必填字段；微信昵称仅用于辅助检查，未检索到时留空，
不阻止缓存保存、复用或导出。仅两份身份的微信昵称均非空时才比较微信昵称是否冲突。
身份字段缺失时列出车群、单号、订单昵称、原始行号和具体缺失字段。
需要补查的订单无法匹配群成员时，汇总各车所有未检测到成员的单号与订单昵称，
提示检查订单版本、群昵称编号与群成员情况，并中止导出，保留旧映射。
原始订单第二个 sheet 第三行必须包含 `收货人姓名`、`收货人联系方式`、`收货人地址` 表头。
优先按订单单号匹配群昵称开头编号，未命中时按订单昵称精确匹配微信昵称或完整群昵称，
不使用模糊匹配。跨车按 wxid 合并；身份无法唯一确定、wxid 缺失、单号与昵称指向不同成员、
同一 wxid 对应不同订单昵称，或必需订单字段缺失时中止并提示。

工作簿包含「总清单」及各车「补邮清单」，商品内容保留数量，合发列显示「是／否」。
总清单以 `wxid、微信昵称、订单昵称、合发` 开头；补邮清单以 `微信昵称、订单昵称、合发` 开头，
不输出 wxid。微信昵称采用最靠前参与车中的昵称；同名但不同 wxid 的成员分别保留。
同一成员同车多单保留所有单号并汇总商品，合发标记按参与的不同车数量计算。
每人仅进入其参加的最靠前车补邮清单，单车成员也进入对应清单；没有成员的清单保留表头。
姓名、联系方式、地址统一采用最靠前参与车的信息，跨车信息不一致或所选信息缺失时提示，
归属车没有收货地址时，按车序采用其他参与车中最靠前有地址订单的整组收货信息，并提示核对；
所有车都没有地址时保留空值并提示补充。问题按补邮归属车分组、逐行编号，车群反馈之间空一行。
输出保存在 `orders/output/`，回复提供文件入口。
同车多单收货信息冲突时，采用原始文件最靠前订单的信息并提示。

这是一个用于金属徽章无盈利拼团的程序，目的是帮助车主核对成员、计算均摊、计算大货。（当前版本：v0.4.0_beta）

## 📖 使用说明

### Step0. 数据库密钥输入

初次运行程序时，会弹出要求用户输入 key 的窗口。可以使用 wx_key 等工具获取文字 key 之后输入。（**测试版在 wx_decrypt 文件夹内提供了 wx_key。如果使用 wx_key，请确保程序路径为纯英文**，否则 wx_key 会闪退。不需要图像 key。）

<img src="./README.assets/image-20260910153302867.png" alt="image-20260910153302867" style="zoom:50%;" />

输入过的 key 会本地缓存，解密的数据库信息也缓存在本地。输入一次key之后，同一账号在同一设备上，（在wx大版本更新前，应该）不需要再次输入 key。但是更换账号或者更换设备后，需要重新获取 key 并输入。



**补充说明：**

key 是微信数据库解密密钥，用于解析聊天记录。需要注意的是，在目前的微信版本，程序不支持自动解码微信本地数据库，且可以自动解码的微信版本已无法使用安装包进行安装。因此，如果要使用本程序，需要用户自行获取 key 并主动输入。

**本程序只会在你的授权下访问你自己的微信本地数据库，不会把你的数据上传至互联网。如果有对数据泄露或封号的担忧，请勿使用本程序。使用前请务必知悉。**



### Step1. 待处理信息录入

![image-20260910153429943](./README.assets/image-20260910153429943.png)

程序启动后，会显示如上界面。每一个对话会被当成一车，对话会按照创建时间进行排序，对话记录会在本地保存。



**点击新对话之后，需要输入以下信息：**

1️⃣**群聊名称**：输入车群名称。群聊支持模糊检索，并且后续再次录入时可以修改。建议输得尽量准确，避免名称有相同词语的群聊被错误识别。

群聊名称输入后，当前对话会显示群聊名称。

> 输入示例1：群聊 一家人，订单 yjr
>
> 输入示例2：群聊 相亲相爱一家人

**2️⃣订单**：用于查群成员昵称是否备注正确、以及计算均摊的订单。

目前，**需要把自助拼单的订单文件上传至程序根目录的 orders 文件夹内**（建议重命名为简单的名称）。下载下来的.xlsx文件直接导入即可。输入订单名称时可以不需要输入.xlsx后缀。

也可以自定义文件输入输出路径，但是并不推荐。这个暂未经过完整测试，运行中可能会出现大量的错误。



### Step2. 特殊成员名单输入

> 输入示例 1：车主 xxx，单号 7，参摊
>
> 输入示例 2：画师 xxx
>
> 输入示例 3：车主 xxx，工具人 xxx

特殊成员名单支持：

| 特殊成员 | 人数限制        | 是否必须设置 |
| -------- | --------------- | ------------ |
| **车主** | 必须且只能 1 人 | **必须**     |
| 画师     | 最多 1 人       | 可选         |
| 章稿画师 | 最多 1 人       | 可选         |
| 供稿人   | 最多 1 人       | 可选         |
| 工具人   | 可以有多人      | 可选         |

特殊成员默认不参摊，如果参摊需要额外备注。

单人特殊成员（车主、画师、章稿画师、供稿人）共用以下修改规则：

- `章稿画师改为小李`、`把车主换成小李`：省略字段时默认修改昵称。
- `画师的群昵称改为013 小李`、`供稿人单号改成13`：修改指定字段。`画师改为13`中的 `13` 是昵称。
- 修改会清空其他身份参数（昵称、群昵称、单号），保留参摊设置，后续成员检查根据新身份重新匹配补全。一次提供多个字段可写 `画师昵称改为小李，单号=13`。
- `清空车主单号`、`把画师的群名片删掉`、`供稿人昵称重置`：只清空指定字段，其余参数保留；后续检查可能再次补全空字段。最后一个身份参数被清空时，移除该成员。
- `删除章稿画师`、`清空车主信息`、`把画师去掉`、`重置供稿人`：未指定字段时移除整个成员。支持删除、删掉、删去、移除、清空、清除、去掉、重置等动作。
- 修改不存在的角色、无效单号或不支持的字段会提示错误。`不要删除车主`、`怎么删除车主`不执行修改。普通设置如 `车主：昵称=小李`仍按原规则补充或覆盖提供的字段。
- 新增、修改、清空和移除成员均直接保存，再展示本次操作对象的信息；删除时展示被移除的记录。所有实际变更都会使旧成员检查和均摊结果失效。多人角色暂不支持上述清理指令，原有带成员定位的字段修改保留。

支持只输入部分信息，例如只输入单号或者只输入昵称。在查成员阶段，程序会自动补齐可检索到的信息并更新。目前已支持在无法准确匹配的时候进行模糊匹配，例如搜索“麦乐鸡”可以在没有其他同名人的时候自动匹配到“麦乐鸡侠🐻”。



### Step3. 商品参摊情况设置

默认参摊情况：

- 目前默认没有特殊说明的商品都是本体，参与均摊。含有“特典”关键词的商品也计入均摊。
- 含有“底胚”关键词的商品不参与个数摊。
- 含有“摊画师……”“摊稿主……”“……专拍”等关键词的订单不计入均摊。

如果没有需要修改的特殊配置，可以跳过这一步。

**可以通过对话修改商品参摊情况**，也可以手动修改 `orders/config/<群名>_商品配置.csv` 的“计入均摊”列（`True` / `False`）。

- `商品底胚参摊`、`商品小猫不参摊`：只检索商品，名称支持完整名称或节选。
- `成员小王不参摊`、`成员单号12不参摊`：只检索成员。普通成员直接加入“其他不参摊成员”；已有特殊成员保留原身份。`成员小王参摊`可恢复参摊，普通成员本来就参摊时无需新增身份。
- `小猫不参摊`：未写对象类型时先检索商品，完全没有商品匹配才检索成员。商品出现多个候选时不会转去检索人员。
- 名称检索优先精准匹配，再模糊匹配；多个候选时回复“选择1”等选定对象。独立均摊金额录入也使用同一商品检索规则，有歧义时请用完整名称或商品序号重新录入金额。
- 参摊修改唯一匹配后立即保存并预览该对象，不再等待“确认”。匹配到多个对象时先列出候选，回复“选择1”等选定后直接保存；选择前可取消或补充名称。候选选择可随对话恢复，选择前订单或配置发生变化则需要重新输入指令。旧版待确认修改草稿会清除并提示重新输入，不会自动执行。
- 修改只保存设置，不开始计算；单对象操作只展示该对象，批量操作只展示涉及的对象。已保存的修改不能通过回复“取消”撤销，需要再输入修改指令。下一次计算仍需确认完整配置。
- 商品开关同时影响人头摊和个数摊；成员不参摊会排除其对应单号的整张订单。商品名称规则仅用于初始化，用户明确保存的配置不会在同步或计算时被覆盖。
- 特殊身份商品设为参摊后，不再仅凭该商品自动新增不参摊成员；已存在的成员身份和参摊状态仍保留，需要单独修改。



### Step4. 操作指令

1️⃣**“查成员”**：检查群昵称和订单是否匹配。

> 输入示例：查成员

算均摊、算大货前会自动检查成员。所以如果需要执行后续操作，这一步可以不手动执行。



2️⃣**“算均摊”**：支持人头摊、个数摊，多款商品时支持独立均摊计算与拉通均摊计算**（默认拉通）**。

均摊录入与计算分开执行。只输入方式、总金额或商品独立金额时，只保存配置，不查成员、不计算。

> 拉通示例：输入“个数摊400” → 输入“算均摊” → 检查商品配置 → 输入“确认计算”。
>
> 独立示例：输入“独立人头摊” → 输入“1号80元，2号40元” → 输入“算均摊” → 检查商品配置 → 输入“确认计算”。
>
> 也可以输入“算均摊，拉通人头摊600”，保存参数后进入商品确认环节。

**每次发起均摊计算，都会先展示群聊、订单、均摊配置、全部商品和全部特殊成员，确认后才查成员。**缺少金额、独立金额合计与总均摊不一致时，先提示补充或修改。确认期间订单或配置改变，需要重新确认。“忽略名单问题，继续计算”只能继续已经确认过商品配置的计算，不能跳过商品确认。

等待商品配置确认时，可输入“计算”“算”“算吧”“无误”“没问题”“下一步”“继续”等继续执行；这些简短表达仅在等待确认时生效。确认同时修改金额或方式时，会重新展示配置。普通确认不会忽略名单核对问题。

**“查看均摊”“看看均摊”“均摊是多少”“查均摊”均为只读查询。**输出顺序与计算完成后的摘要一致：均摊类型 → 总均摊（独立模式另列各商品金额）→ 参摊人数或个数（个数模式另列各商品数量）→ 单人或单个商品均摊。独立人头模式逐商品展示人数和每人金额，总人数去重。未计算时显示“待计算”；订单、配置或特殊成员变化后，旧结果显示为失效，需要重新计算。

均摊类型与计算方式分行展示，金额保留两位小数、不附加单位，例如：

```text
均摊类型：人头摊
计算方式：拉通
总均摊：50.00
参摊人数：6 人
单人均摊：8.34
```

旧对话没有新版计算结果记录、但关联的商品配置 CSV 保存了单份均摊时，查询会展示“历史配置记录”。没有保存的实际参摊人数和数量标注“历史记录未保存”，不会根据金额倒推或直接使用商品总数量。历史金额不代表已经校验适用于当前订单；已明确失效的结果不会通过历史 CSV 重新变为有效。

订单反馈中，`orders/input` 内的文件只显示文件名（包含子目录中的文件），其他位置显示绝对路径；内部仍使用完整路径处理订单。

计算个数摊时，底胚默认不参摊，特典默认参摊。**计算前会检查订单，是否有人只拍了底胚、没有入本体。**（但是有多款商品、要求拥有对应本体的情况暂时无法识别，功能开发中。）

**均摊计算会排除不参摊的特殊成员的订单（例如车主默认不参摊）。**商品是否计入均摊以商品配置为准；底胚、专拍以及可识别的画师／供稿类特殊商品首次创建时默认不参摊，可通过上述指令直接修改。

输入的均摊会被保存在当前对话的商品配置文件中。同一对话恢复后可继续使用；重新输入“算均摊”仍需确认商品配置。

**人头／个数或独立／拉通发生变化时，会清空各商品均摊及单份均摊，旧确认和旧结果失效。**总均摊、商品参摊设置和大货字段保留。切到拉通时，用保留的总均摊重新写入；切到独立时，需要重新录入各商品金额。重复输入相同方式不清空；只修改人头／个数时保留当前独立／拉通范围，新任务默认拉通。同一句切换并录入金额时，先清旧值再写新值。

商品配置通过同目录的 `.owner.json` 文件绑定所属对话。删除对话会一起归档配置及归属文件；同群名、同订单的新对话不会自动继承旧金额（包括总均摊）。来源不明或属于其他对话的遗留配置保存在 `orders/archive/unclaimed/`，不会静默套用。现有旧对话明确关联的配置可在首次打开时迁移保留。

均摊流程回归测试：`python -m unittest discover -s tests -v`。测试使用临时订单与数据库，微信群成员接口使用模拟数据。



**3️⃣“算大货”**：计算大货。计算的过程其实就是导出自助拼单表格的总金额。

计算大货之前，会展示群聊、订单、全部商品的数量、单价、大货总价和全部特殊成员，不展示均摊摘要及商品均摊字段，并提示车主检查单价变动、商品价格同步、均摊抵扣大货等情况，确认之后才会继续大货计算。

> 输入示例：算大货

**“均摊大货一起算”“均摊和大货一起算”“均摊大货总金额”**：先确认均摊配置，再确认大货配置，两次确认完成后查成员、计算均摊和大货，生成 `orders/output/<群名>_均摊大货总金额.csv`，同时在对话中展示表格。列顺序为“单号、昵称、总金额、均摊金额、大货金额”，总金额为均摊金额与大货金额之和，不显示总金额为 0 的成员。不参摊成员的均摊金额为 0，大货金额仍保留；大货沿用订单原“总金额”。确认期间订单或配置变化时，需要重新确认；名单核对未通过时停止两项计算。



## 📄 输出文件说明

* **程序处理后的输出文件默认保存在 orders/output 文件夹；**原始文件默认从程序根目录的 orders 文件夹进行读取
* 自助拼单的订单简化后，是后缀为 parsed_orders.csv 的文件
* 商品**均摊计算结果（输出每人需要支付的均摊）**，以拉通均摊为例，是后缀为 parsed_orders_share_head_flat（拉通人头摊）或者parsed_orders_share_quantity_flat（拉通个数摊）的**包含”share“关键词的 csv 文件**
* 大货计算结果（输出每人需要支付的大货金额）是包含”bulk“关键词的csv文件

- 商品配置文件 product_config 记录商品的信息，包括以下参数：

| 字段         | 什么时候更新      | 含义                                 |
| ------------ | ----------------- | ------------------------------------ |
| 商品序号     | 解析订单后        | 当前商品序号                         |
| 商品名称     | 解析订单后        | parsed orders 中商品                 |
| 商品数量     | 解析订单后        | 全部订单总数量                       |
| 计入均摊     | 首次创建/用户修改 | 是否参与均摊                         |
| 均摊类型     | **算均摊前**      | 四种类型之一                         |
| 商品均摊     | **算均摊前**      | 拉通=总均摊；独立=该商品自己的分均摊 |
| 单份均摊     | **算均摊后**      | 实际每人/每件收取的均摊              |
| 商品单价     | **算大货前**      | sheet1 读取                          |
| 商品大货总价 | **算大货前**      | 商品数量 × 商品单价                  |

### 订单录入、查询与比较

- 一次录入两个订单：`新订单bbb，旧订单aaa`；明确标签优先。
- 编号录入：`订单1 aaa，订单2 bbb`，支持编号0–2，较小编号为旧订单，较大编号为新订单，输入顺序不影响角色。找不到 `aaa.xlsx` 时再尝试 `1 aaa.xlsx`，其他编号不作序号解释。
- 无标签录入：`订单aaa,订单bbb`、`订单是aaa，订单是bbb`、`订单 aaa, 订单  bbb`，第一个为旧订单，第二个为新订单。支持冒号、等号、分号、换行及成对引号。可省略 `.xlsx`，文件默认来自 `orders/input/`。
- 两个文件都验证成功后一起更新；失败或重复文件不更新该组订单。单订单录入继续沿用版本顺移规则；`旧订单aaa` 只更新旧订单。
- `查看订单`、`看看订单`、`订单是什么`、`告诉我订单名称`：只读展示新订单、旧订单和两个历史缓存。
- `比较订单`、`比对订单`、`对比订单`、`看看订单有什么变化`：默认旧订单→新订单，先展示所选文件，回复 `确认比较` 后执行，`取消比较` 取消。可用 `比较新订单和缓存1` 指定版本。
- 等待期间所选版本、文件内容或群聊名称变化，需要重新确认。待比较选择可随对话恢复；比较不读取微信群成员，也不修改均摊配置。
- 按单号匹配，比较昵称、总金额、商品数量以及新增/删除的订单和商品；重复单号会提示无法可靠比较。此报告比较订单解析器提取的业务字段，不比较收货地址等其他字段。
- 报告保存到 `orders/comparisons/群聊名称_订单比较_旧订单名_新订单名.csv`，如 `orders/comparisons/一家人_订单比较_aaa_bbb.csv`。名称去掉原扩展名，无差异也保存报告；同名报告追加 `_2`、`_3`，不覆盖历史报告。CSV使用带BOM的UTF-8编码，可用Excel查看。
